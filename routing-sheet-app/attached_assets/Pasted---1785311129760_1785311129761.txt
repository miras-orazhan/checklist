# Техническое задание
## Веб-приложение «Цифровой обходной лист» (мультиформа) для процесса найма

Версия: 1.1 (обновлено по итогам уточнений от 15.07.2026)
Дата: 15.07.2026

---

## 0. Журнал зафиксированных решений (по итогам уточнений)

- Признак «Врач» (`is_doctor`) выставляет **HR** — галочкой, по должности, на шаге «Оформление».
- Разница между маршрутом врача и не-врача — **только** в двух фоновых задачах: врачебная анкета (глав. врач) и публикация на сайтах (аккаунт-менеджер). Остальные шаги идентичны.
- Роли сотрудникам (кто HR, кто ТБ, кто IT и т.д.) назначает **администратор** системы.
- Уточнён порядок писем при принятии оффера: письмо №1 — приглашение с кнопкой «Принять»; после клика — страница ввода одноразового кода; код приходит письмом №2.
- Кандидат видит только упрощённый статус — пройден/не пройден по каждому отделу, без деталей.
- Каждый отдел (роль) может оставить примечание (свободный текст) к своему шагу.
- Передача данных в Bitrix24 — через API.
- Email-провайдер — Gmail через Google Apps Script.
- Типовая продолжительность всего маршрута — 1–2 часа.
- При увольнении: если кто-то из согласующих отклоняет — процесс останавливается; восстановить (если отклонили по ошибке) может администратор в течение часа после отклонения.
- Увольняемый сотрудник получает уведомление о статусе по почте — аналогично кандидату, тоже одноразовая ссылка/страница.
- Маркетолог загружает фото для всех сотрудников без исключения.
- Обходной лист **приёма** можно закрыть, даже если не все шаги выполнены (например, если в филиале нет какой-то роли — шаг может подтвердить вручную рекрутер или HR); для врачей допускается закрытие **без** врачебной анкеты и публикации на сайтах (это фоновые, не блокирующие задачи).
- Обходной лист **увольнения** врача, наоборот, **нельзя** закрыть без подтверждённого удаления публикации с сайтов — это блокирующее условие.

## 1. Назначение и цели системы

Система автоматизирует два маршрута:
- **Приём на работу** — от согласия кандидата на оффер до полной готовности его аккаунтов, документов и публикации профиля на внешних площадках (см. разделы 3–8).
- **Увольнение** — от инициации заявки специалистом по кадрам до сбора всех согласований и (для врачей) удаления профиля с внешних сайтов (см. раздел 9).

Оба маршрута реализуются в одной системе, на единой платформе ролей и мультиформы: каждое подразделение видит и заполняет только свой блок формы.

Ключевые цели:
- Кандидат не регистрируется отдельно — профиль создаётся автоматически по персональной защищённой ссылке.
- Каждое подразделение (HR, ТБ, IT, маркетинг, главный врач, аккаунт-менеджеры, аудит) видит только свой участок формы и свои задачи.
- Рекрутер и руководство в любой момент видят статус обходного листа целиком (единый прогресс-трекер).
- Реальные интеграции: почтовые/мессенджер-рассылки, Bitrix24, SMS.

## 2. Роли и права доступа

| Роль | Доступ | Что делает |
|---|---|---|
| **Кандидат** | Только по персональной одноразовой ссылке, без пароля | Принимает оффер, видит статус своего обходного листа |
| **Рекрутер** | Личный кабинет (логин/пароль или SSO) | Создаёт оффер, заполняет ФИО/почту/телефон/опыт/образование/курсы, финально сверяет все данные |
| **Отдел кадров (HR)** | Личный кабинет | Оформляет кандидата, заполняет Филиал и Должность, ставит отметку «Оформлен» |
| **Маркетинг** | Личный кабинет / упрощённая форма | Загружает фото сотрудника — **для всех должностей**, не только врачей |
| **ТБ (охрана труда)** | Личный кабинет / упрощённая форма | Отмечает факт проведения инструктажа (без заполнения полей) |
| **IT** | Личный кабинет | Получает автоматические данные по вебхуку (система сама создаёт задачу в Bitrix24); после фактического создания аккаунта отмечает выполнение |
| **Главный врач филиала / зам. глав. врача** | Личный кабинет, видит только своих кандидатов-врачей | Заполняет стаж, специальность (с возрастными ограничениями и скидками для сайтов), «О враче», перечень процедур |
| **Аккаунт-менеджер** | Личный кабинет, задачи только по врачам | Видит врачебную анкету **полностью, но только в режиме просмотра** (без права редактирования); получает задачу на публикацию врача на сайтах, отмечает выполнение |
| **Департамент аудита** | Личный кабинет | Отмечает факт обучения корпоративным стандартам |
| **Администратор системы** | Полный доступ | Настройка маршрутов, филиалов, шаблонов писем; **назначение ролей сотрудникам** (кто HR, ТБ, IT и т.д.); восстановление ошибочно остановленных обходных листов увольнения |

Права разграничены на уровне формы: каждая роль видит и редактирует только свой блок полей, но видит статус остальных блоков (только просмотр).

## 3. Бизнес-процесс (маршрут обходного листа)

### Этап 0. Оффер
1. Рекрутер в своём кабинете создаёт карточку кандидата: ФИО, почта, телефон, опыт работы, образование, курсы повышения квалификации.
2. Система генерирует персональную одноразовую защищённую ссылку (токен) и отправляет кандидату email/сообщение в мессенджер с текстом оффера и кнопкой «Принять предложение».

### Этап 1. Принятие оффера кандидатом
1. Кандидат переходит по ссылке из письма №1 (приглашение с кнопкой «Принять»).
2. После нажатия «Принять» кандидат попадает на страницу ввода одноразового кода.
3. Система отправляет этот код отдельным письмом №2 (второе письмо — только с кодом).
4. Кандидат вводит код на странице; при совпадении — оффер считается принятым.
5. Система автоматически создаёт профиль кандидата (ФИО, почта — из данных рекрутера), отдельная регистрация не требуется.
6. Кандидат сразу перенаправляется на персональную страницу обходного листа (в рамках той же одноразовой сессии/ссылки); дополнительно на почту приходит письмо-подтверждение с прямой ссылкой на эту страницу — на случай, если кандидат вернётся позже.

### Этап 2. Параллельно-последовательные шаги обходного листа
После принятия оффера система создаёт задачи (карточки) для участников маршрута. Часть шагов идёт последовательно (зависит от результата предыдущего), часть — параллельно.

| № | Шаг | Исполнитель | Действие | Зависимость |
|---|---|---|---|---|
| 1 | Оформление | Отдел кадров | Заполняет Филиал, Должность; ставит галочку «Оформлен» | После принятия оффера |
| 2 | Фото | Маркетинг | Загружает фото сотрудника — **для всех должностей** | После оформления HR |
| 3 | Инструктаж по ТБ | ТБ | Отмечает «Инструктаж проведён» | Параллельно с HR/маркетингом |
| 4 | Создание аккаунтов | Система → IT | Система автоматически отправляет данные по **вебхуку**, по которому в Bitrix24 создаётся задача; IT ничего не инициирует вручную, только отмечает «Аккаунт создан» после фактического создания | Стартует автоматически сразу после оформления HR (без ручной заявки IT) |
| 5 | Врачебная анкета *(фоновая задача)* | Главный врач филиала (или зам) | Заполняет стаж, специальность (с возрастными ограничениями/скидками для сайтов), «О враче», процедуры | Только для должности «врач»; выполняется в фоне и не блокирует остальные шаги маршрута |
| 6 | Публикация на сайтах *(фоновая задача)* | Аккаунт-менеджер | Видит врачебную анкету полностью, но **только в режиме просмотра** (без права редактирования); получает задачу «Опубликовать врача на сайтах», отмечает выполнение | Только для врачей; запускается только после того, как заполнена врачебная анкета **и** загружено фото |
| 7 | Обучение стандартам | Департамент аудита | Отмечает «Обучение пройдено» | Параллельно, независимо от других |
| 8 | Финальная сверка | Рекрутер | Проверяет все данные по кандидату, закрывает обходной лист | После завершения всех шагов выше |

> Важно: шаги 2, 5, 6 применяются **только к должности «врач»**. Для прочих должностей маршрут короче: HR → ТБ / IT / Аудит → финальная сверка рекрутера.

### Этап 3. Завершение
Когда все обязательные для данной должности шаги отмечены, статус обходного листа переходит в «Завершён», кандидату и рекрутеру приходит уведомление.

Особые правила закрытия:
- Врачебная анкета и публикация на сайтах — фоновые задачи, **не блокируют** закрытие обходного листа приёма: лист может быть закрыт, даже если эти два шага ещё не выполнены (они донастраиваются позже).
- Если в филиале отсутствует сотрудник конкретной роли (например, нет отдельного маркетолога), соответствующий шаг может вручную подтвердить **рекрутер или HR** — как временная замена ответственного.

## 4. Функциональные требования

### 4.1 Мультиформа
- Единая карточка кандидата = набор блоков (виджетов), каждый привязан к роли.
- Блок редактируется только назначенной ролью, остальным доступен в режиме просмотра.
- Автосохранение и история изменений (кто, когда, что изменил).
- **Примечания**: каждый блок (шаг) содержит необязательное поле «Примечание» — свободный текст, который заполняет ответственная роль; видно всем участникам маршрута в режиме просмотра.
- Условная логика: блок «Фото» показывается для **всех** должностей. Блоки «Врачебная анкета» и «Публикация на сайтах» показываются только если должность = «Врач» (справочник должностей должен содержать признак `is_doctor`).
- Блок «Публикация на сайтах» дополнительно недоступен (заблокирован), пока не заполнена врачебная анкета и не загружено фото — это условие активации фоновой задачи для аккаунт-менеджера.
- Блок «Врачебная анкета» доступен аккаунт-менеджеру в режиме **только чтения** (полный просмотр, редактирование запрещено).

### 4.2 Прогресс-трекер
- Визуальная шкала/чек-лист статусов обходного листа (аналог «traffic light»): не начато / в работе / готово.
- Доступен рекрутеру, HR, главному врачу (по своим кандидатам) и администратору — общий дашборд по всем кандидатам с фильтрами (филиал, должность, статус, срок).

### 4.3 Уведомления
- Автоматические email/мессенджер-уведомления на каждом переходе этапа (кандидату — при готовности обходного листа; ответственному — при поступлении новой задачи; рекрутеру — при завершении).
- Эскалация: если задача «висит» дольше N дней (настраиваемый SLA) — напоминание ответственному и уведомление его руководителю.

### 4.4 Кандидатская страница
- Без регистрации, доступ по токенизированной ссылке (срок жизни ссылки ограничен, например 72 часа, с возможностью перевыпуска).
- Кандидат видит только упрощённый статус — **пройден / не пройден** по каждому отделу/шагу, без деталей заполнения (без доступа к содержимому врачебной анкеты, примечаниям других ролей и т.п.).

### 4.5 Реальные интеграции
- **Email**: **Gmail через Google Apps Script** — используется как транзакционный email-провайдер для всех писем (приглашение, код, ссылка на обходной лист, уведомления ролям).
- **Мессенджеры**: отправка ссылки в WhatsApp/Telegram (через API провайдера) как альтернативный/дублирующий канал — состав провайдера уточняется отдельно.
- **Bitrix24**: передача данных выполняется через **Bitrix24 REST API** — система напрямую отправляет данные для создания задачи/аккаунта; IT не инициирует запрос вручную, только фиксирует факт создания.
- **SMS**: опциональный дополнительный канал уведомлений; **не используется** для передачи одноразового кода при принятии оффера — код отправляется email-письмом (см. раздел 3, Этап 1).

### 4.6 Безопасность
- Персональные ссылки — на основе криптографически стойких одноразовых токенов (UUID v4 + подпись), не должны быть предсказуемыми.
- Ограничение по времени жизни токена и по количеству попыток ввода кода.
- Шифрование персональных данных кандидата в базе (в т.ч. при хранении фото и врачебных данных).
- Соответствие требованиям законодательства о персональных данных (согласие кандидата на обработку ПДн — отдельный чекбокс при принятии оффера).
- Логирование всех действий (аудит-лог) с указанием роли, пользователя, времени.

## 5. Модель данных (укрупнённо)

- **Candidate** (id, ФИО, email, телефон, опыт_работы, образование, курсы, статус_оффера, ссылка_токен, дата_принятия)
- **Offer** (id, candidate_id, дата_отправки, статус, кто_отправил)

- **Notification** (id, тип, получатель, канал, статус_отправки, дата)
- **AuditLog** (id, кто, действие, объект, дата)

## 6. Архитектура системы (укрупнённо)

```
[Email / Мессенджер провайдер] <--> [Backend API] <--> [PostgreSQL]
                                        |
                    -----------------------------------------
                    |            |            |             |
              [Bitrix24 API] [SMS-провайдер] [Frontend SPA] [Файловое хранилище (фото)]
```

- **Backend**: REST/GraphQL API, аутентификация сотрудников (JWT/SSO), отдельный безопасный эндпоинт для доступа кандидата по токену.
- **Frontend**: SPA (React) с ролевым интерфейсом — «конструктор» из блоков-виджетов формы, рендерящихся по правам роли.
- **БД**: реляционная (PostgreSQL) — данные кандидатов, маршрутов, статусов.
- **Файловое хранилище**: для фото врачей (S3-совместимое хранилище).
- **Очередь задач**: для асинхронной отправки писем/SMS и запросов в Bitrix24 (например, через message-брокер), чтобы не блокировать основной поток.
- **Планировщик**: для эскалаций по SLA и напоминаний.

## 7. Нефункциональные требования

- Отказоустойчивость интеграций: повторные попытки (retry) при сбое отправки письма/запроса в Bitrix24.
- Аудируемость: полная история изменений по каждому кандидату.
- Масштабируемость: система должна поддерживать несколько филиалов и параллельный найм десятков кандидатов одновременно.
- Локализация: интерфейс на русском языке (с возможностью расширения).
- Адаптивность: кабинеты ролей и страница кандидата должны корректно работать на мобильных устройствах (кандидат чаще всего открывает ссылку с телефона).
- **Типовая продолжительность маршрута**: полный обходной лист (приём или увольнение) при отсутствии задержек занимает **1–2 часа**. Это ориентир для настройки SLA и порогов эскалации (раздел 4.3) — конкретные пороги по каждому шагу уточняются отдельно.

## 9. Обходной лист при увольнении

### 9.1 Назначение
Второй маршрут в той же системе — оформление увольнения сотрудника. Логика аналогична приёму: единая карточка увольнения, разбитая на блоки по ролям, каждая роль видит только свой блок, статус агрегируется в общий прогресс-трекер.

### 9.2 Инициация
Заявку на увольнение создаёт специалист по кадрам (отдел кадров) — вручную, на основании заявления сотрудника или решения руководителя. При создании заявки указываются: ФИО сотрудника, филиал, должность (в т.ч. признак `is_doctor` — подтягивается автоматически из карточки сотрудника), дата увольнения, инициатор.

После создания заявки система автоматически рассылает задачи всем ответственным ролям (см. 9.3) — большинство шагов идёт **параллельно**, так как это независимые согласования, а не последовательная цепочка.

### 9.3 Роли, действия и объём заполнения

> Дополнительно: к каждому шагу ниже применяется общее правило — ответственная роль может оставить необязательное примечание (свободный текст), видимое остальным участникам маршрута (см. раздел 4.1).

| № | Роль | Действие | Что заполняет |
|---|---|---|---|
| 1 | Главный врач филиала | Отмечает согласие на увольнение | Только чекбокс «Согласовано» (+ опционально комментарий) |
| 2 | IT | Получает заявку на отзыв учётных данных сотрудника (в т.ч. Bitrix24 и др. системы), отмечает выполнение | Чекбокс «Учётные данные отозваны» |
| 3 | Маркетинг | Отмечает согласие на увольнение | Чекбокс «Согласовано» |
| 4 | Бухгалтерия | Отмечает согласие на увольнение (расчёт, обходной по матответственности и т.п.) | Чекбокс «Согласовано» |
| 5 | Департамент безопасности | Отмечает согласие на увольнение | Чекбокс «Согласовано» |
| 6 | Отдел кадров — менеджер по адаптации | Проводит exit-интервью, отмечает согласие | Заметки/результат интервью (текстовое поле) + чекбокс «Согласовано» |
| 7 | Отдел кадров — специалист по кадрам | Отмечает согласие на увольнение (финальное оформление документов) | Чекбокс «Согласовано» |
| 8 | Инженер по мед. оборудованию | Отмечает согласие на увольнение (сдача оборудования/инструментов) | Чекбокс «Согласовано» |
| 9 | Аккаунт-менеджер *(только если сотрудник — врач)* | Получает заявку на удаление профиля врача с внешних сайтов, отмечает выполнение | Чекбокс «Профиль удалён с сайтов» |

> Условная логика: шаг 9 создаётся автоматически, только если `is_doctor = true`. Для остальных должностей маршрут состоит из шагов 1–8.

### 9.4 Завершение маршрута
- Обходной лист увольнения считается закрытым, когда все применимые к должности шаги отмечены как выполненные/согласованные.
- **Исключение для врачей**: в отличие от маршрута приёма, при увольнении шаг «Публикация на сайтах» (удаление профиля аккаунт-менеджером) — **блокирующий**. Лист увольнения врача нельзя закрыть, пока профиль не удалён с сайтов.
- Если в филиале отсутствует ответственный за какой-то шаг, его может подтвердить вручную рекрутер или HR (аналогично маршруту приёма).
- Финальное закрытие фиксирует специалист по кадрам (шаг 7) — после того как получены все обязательные согласования, включая (для врачей) удаление профиля.
- По закрытию — уведомление специалисту по кадрам, руководителю и (опционально) в Bitrix24 об изменении статуса сотрудника на «уволен».

### 9.4.1 Отклонение согласования
- Если любая из ролей **отклоняет** согласование (не даёт согласие), весь процесс увольнения останавливается — статус обходного листа переходит в «Отклонён/Остановлен», дальнейшие шаги не выполняются.
- Восстановить остановленный по ошибке процесс (например, при случайном отклонении) может **администратор** — в течение **1 часа** с момента отклонения. По истечении часа восстановление недоступно, требуется повторная инициация процесса.

### 9.4.2 Уведомление увольняемого сотрудника
- Сотрудник получает уведомление о статусе обходного листа увольнения по email — аналогично кандидатской странице: доступ по **одноразовой персональной ссылке**, без регистрации.
- Видимость аналогична кандидату при приёме: только упрощённый статус (пройдено/не пройдено) по каждому отделу, без деталей согласований.

### 9.5 Прогресс-трекер и уведомления
- Аналогично приёму — визуальный чек-лист по всем 8–9 шагам, доступен инициатору (специалисту по кадрам) и администратору.
- Автоматические напоминания ответственным, если согласование не получено в течение SLA (срок уточняется).
- Эскалация руководителю подразделения при просрочке.

### 9.6 Модель данных (дополнение к разделу 5)

- **TerminationSheet** (id, employee_id, филиал, должность, is_doctor, дата_увольнения, инициатор_id, статус_общий, дата_создания, дата_закрытия)
- **TerminationStep** (id, termination_sheet_id, роль, исполнитель_id, статус, комментарий/данные (JSON, для exit-интервью), дата_обновления)

### 9.7 Открытые вопросы по увольнению

> Вопросы про отклонение согласования и уведомление сотрудника уже решены — см. разделы 9.4.1, 9.4.2 и журнал решений (раздел 0).

1. Обязателен ли exit-интервью (шаг 6) для всех сотрудников или только для определённых категорий?
2. Нужна ли фиксация даты последнего рабочего дня отдельно от даты увольнения (юридической)?
3. Есть ли роли, для которых шаг обязателен только при определённых условиях (например, инженер по мед. оборудованию — только если сотрудник пользовался оборудованием)?
4. Точные пороги SLA по каждому шагу увольнения — совпадают ли с приёмом или отдельные (при увольнении обычно более сжатые сроки)?
